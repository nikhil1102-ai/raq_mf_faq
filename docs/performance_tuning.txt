1. ROOT CAUSE ANALYSIS
================================================================================

The ~15-second response time was caused by a combination of factors:

  a) CORS Pre-flight Overhead (~7s)
     - The browser sent an OPTIONS pre-flight request before every POST to
       /api/ask because the frontend (Vercel) and backend (Railway) are on
       different origins.
     - Without a CORS middleware configured with max_age, the browser
       re-sent the pre-flight on EVERY request, adding a full round-trip
       each time.
     - This explained why PowerShell (no pre-flight) was ~3s but the UI
       was ~10-15s.

  b) Blocking Synchronous Endpoint (~3-5s)
     - The /api/ask endpoint was a synchronous def, meaning the entire
       FastAPI event loop was blocked while the answer() pipeline ran
       (embedding lookup + LLM call).
     - Under concurrent load, requests would queue behind each other.

  c) Slow LLM Model
     - The original model (llama-3.1-8b-instant on Groq) was decommissioned.
     - The replacement model needed to balance quality and speed.

  d) No Query Caching
     - Identical or similar queries re-ran the full pipeline every time.

  e) Railway Cold Starts
     - Railway free tier scales to zero after inactivity, causing a ~10s
       cold-start delay on the first request.

2. FIX #1 – CORS PRE-FLIGHT CACHING (MAJOR IMPACT)
================================================================================

File    : ui/server.py
Impact  : Reduced UI latency by ~7 seconds
Cause   : Browser sent OPTIONS pre-flight on every /api/ask POST request

BEFORE:
  - No CORSMiddleware configured with max_age
  - Every browser request = 2 HTTP calls (OPTIONS + POST)

AFTER:
  app.add_middleware(
      CORSMiddleware,
      allow_origins=["*"],          # Restrict to your Vercel domain in prod
      allow_credentials=True,
      allow_methods=["*"],
      allow_headers=["*"],
      max_age=86400,                # Cache pre-flight for 24 hours
  )

WHY IT WORKS:
  - max_age=86400 tells the browser to cache the pre-flight response for
    24 hours.
  - Subsequent requests skip the OPTIONS call entirely, saving one full
    network round-trip (~500ms–7s depending on connection quality and
    Railway cold-start state).

NOTE:
  - For production, replace allow_origins=["*"] with your specific Vercel
    domain, e.g. allow_origins=["https://your-app.vercel.app"]

3. FIX #2 – ASYNC ENDPOINT WITH THREAD POOL EXECUTOR
================================================================================

File    : ui/server.py
Impact  : Prevents event loop blocking; enables concurrent request handling
Cause   : Synchronous answer() function blocked the FastAPI event loop

BEFORE:
  @app.post("/api/ask")
  def ask(q: Query):
      response = answer(q.query)   # Blocks the event loop for 3-5s
      return response

AFTER:
  from concurrent.futures import ThreadPoolExecutor
  import asyncio, time

  _executor = ThreadPoolExecutor(max_workers=4)

  @app.post("/api/ask")
  async def ask(q: Query):
      loop = asyncio.get_event_loop()
      start = time.time()
      response = await loop.run_in_executor(_executor, answer, q.query)
      elapsed = time.time() - start
      logging.info(f"Answer pipeline completed in {elapsed:.2f}s")
      return response

WHY IT WORKS:
  - The answer() function performs blocking I/O (ChromaDB query + Groq API
    call). Running it in a ThreadPoolExecutor offloads the blocking work
    to a separate thread.
  - The FastAPI event loop remains responsive and can handle other requests
    (health checks, ping, concurrent queries) while waiting.
  - max_workers=4 allows up to 4 queries to be processed in parallel.

4. FIX #3 – LLM MODEL SWITCH
================================================================================

File    : pipeline/llm_client.py
Impact  : Replaced decommissioned model; improved response quality
Cause   : llama-3.1-8b-instant was decommissioned on Groq (Aug 16, 2026)

BEFORE:
  model="llama-3.1-8b-instant"    # Decommissioned
  temperature=0.3
  max_tokens=1024
  top_p=0.9                       # Redundant with low temperature

AFTER:
  model="openai/gpt-oss-20b"      # Available via Groq's OpenRouter
  temperature=0.1                  # Lower for more deterministic answers
  max_tokens=512                   # Sufficient for FAQ responses
  # top_p removed (redundant when temperature is low)

WHY IT WORKS:
  - gpt-oss-20b is a fast, quality model available on Groq's infrastructure.
  - Lower temperature (0.1) produces more consistent, factual responses
    suitable for financial FAQ data.
  - Reduced max_tokens (512 vs 1024) speeds up generation since the model
    stops earlier.
  - Removing top_p avoids conflicting sampling parameters.

RETRY LOGIC:
  - Added a retry loop (up to 2 attempts) in case the model returns an
    empty response, with a safe fallback message.

5. FIX #4 – IN-MEMORY LRU QUERY CACHE
================================================================================

File    : pipeline/qa_pipeline.py
Impact  : Instant responses for repeated/similar queries
Cause   : No caching; identical queries re-ran the full pipeline

IMPLEMENTATION:
  import hashlib
  from functools import lru_cache

  _query_cache = {}
  _CACHE_TTL = 3600  # 1 hour

  def answer(query: str) -> dict:
      cache_key = hashlib.md5(query.strip().lower().encode()).hexdigest()
      now = time.time()

      if cache_key in _query_cache:
          cached_answer, timestamp = _query_cache[cache_key]
          if now - timestamp < _CACHE_TTL:
              logging.info(f"Cache HIT for query: '{query}'")
              return cached_answer

      # ... run full pipeline ...
      _query_cache[cache_key] = (result, now)
      return result

WHY IT WORKS:
  - Repeated queries (common in FAQ apps) return instantly from memory.
  - TTL of 1 hour ensures data freshness (NAV updates daily).
  - MD5 hash of normalized query acts as the cache key.
  - No persistence needed (Railway free tier; cache rebuilds on restart).

9. FIX #8 – JINA AI EMBEDDINGS (REMOVING CPU BOTTLENECK)
================================================================================

File    : retrieval/query_embedder.py, ingestion/embedder.py
Impact  : Reduced query embedding latency from ~13s to ~0.3s
Cause   : Running SentenceTransformer locally on Railway's free-tier CPU
          was severely CPU-bound (took ~13s per query).

BEFORE:
  model = SentenceTransformer("all-MiniLM-L6-v2")
  embedding = model.encode(query)

AFTER:
  # Call Jina AI API directly
  response = requests.post(
      "https://api.jina.ai/v1/embeddings",
      headers={"Authorization": f"Bearer {key}"},
      json={"model": "jina-embeddings-v2-base-en", "input": [query]}
  )

WHY IT WORKS:
  The Problem We Faced (Why it took 13+ seconds):
  - When a user asks a question, the app must convert their text into a string of
    numbers called an embedding vector. It uses this vector to mathematically
    search ChromaDB for similar text chunks.
  - Before the fix, we used `sentence-transformers` to run the neural network
    locally on the server. Neural networks require thousands of complex matrix
    multiplications to generate an embedding.
  - Railway's Free Tier provides only a fraction of a basic CPU. Running that
    heavy math on Railway's tiny CPU was like trying to render a 4K video on a
    smartwatch. It took ~13 seconds just to process one sentence.

  The Solution (Jina AI Embedding API):
  Instead of changing *what* the app does, we changed *where* it does it.
  1. Removed Local Processing: We deleted `sentence-transformers` from
     requirements.txt. The Railway server no longer runs any neural network math.
  2. Delegated to GPUs: When a query comes in, we now send the text via a quick
     HTTP request to Jina AI's API.
  3. Jina's Hardware: Jina AI processes the text instantly using massive,
     enterprise-grade GPU servers, returning the embedding vector to us in
     about 300 milliseconds.

  In short: We took the heaviest, most computationally expensive task in the app
  and outsourced it to a massive GPU server, dropping the processing time from
  13 seconds down to a fraction of a second. This also required a one-time
  re-ingestion since the model changed (384-dim -> 768-dim).
